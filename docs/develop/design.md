# Design guidelines

The display UI is a Nextion project: two HMI files, one layout spec each and a Python page class per panel type. This page holds the rules that keep it consistent — the grid, the eight fonts, the icon set, how a theme reaches a page, the header — and the checklist that adds a panel type.

## Style

The display is 480 × 320 in landscape and 320 × 480 in portrait, split into a header for navigation and the title, and a main area for panel content.

The numbers live in the layout specs — `scripts/hmi_layout/landscape_layout.py` and `portrait_layout.py` — and `make hmi-check` fails when an HMI disagrees with them.

| Rule | Landscape | Portrait |
|------|-----------|----------|
| Screen | 480 × 320 px | 320 × 480 px |
| Visible width | 450 px; the bezel hides x = 450..479 | 320 px |
| Side margin | 12 px, content ends at x 438 | 12 px, content spans x 12..308 |
| Header height | 50 px | 50 px |
| Gutter between controls | 8 px | 8 px |
| Header function buttons | 50 × 50 px | 50 × 50 px |
| Grid tiles | 140 × 123 px with 4 px gaps, 3 × 2 | 2 × 3 re-flow |
| Row pages | 51 px pitch, 40 px slider bar | rows stack, sliders taller |
| Slider track / knob | 30 px high, 25 px knob | taller, no knob on fill bars |

Touch sizes follow the same grid: header buttons are 50 × 50 px, a grid tile 140 × 123 px with its 48 × 48 px power button, a row 51 px high, and a six-across button row is 50 px tall at x 12, 87, 162, 237, 313, 388.

- Keep interactive content left of x 450 in landscape. Touches in the hidden band are valid, but nothing is visible there.
- Picture-only pages (Clock, Clock Two, Weather, System) use the whole height and set `USE_SYSTEM_COLORS = False`.
- Alignment is compiled per widget. The layout spec writes geometry, the slider cursor (`wid`, `hig`, `pco`) and `sendkey`; `scripts/hmi_layout/theme.py` writes the theme colours. Set alignment and every other attribute in the Nextion Editor, in both projects ([the HMI↔Python contract](nextion-editor.md#the-hmipython-contract)).

## Fonts

Text is drawn in [Roboto](https://github.com/googlefonts/roboto); icons are glyphs of [MaterialDesign-Webfont](https://github.com/Templarian/MaterialDesign-Webfont) baked into the same fonts. The display has eight fonts, and the font ID — what `.font=` commands and the alarm keypad's font option use — grows with the size.

| Font ID | Size | Face | Use |
|---------|------|------|-----|
| 0 | 20 px | Roboto Regular | small text and icons |
| 1 | 24 px | Roboto Regular | default text and icons |
| 2 | 32 px | Roboto Regular | large text and icons |
| 3 | 48 px | Roboto Regular | larger text and icons |
| 4 | 72 px | Roboto Regular | time, weather and large values: limited text and icons |
| 5 | 96 px | Roboto Light | time, weather and large values |
| 6 | 128 px | Roboto Light | time, weather and large values |
| 7 | 164 px | Roboto Light | time, weather and large values |

The fonts are the `.zi` files in `nextion/fonts/` (`Roboto-Regular <size> (UTF_8).zi`, `Roboto-Light <size> (UTF_8).zi`), generated by `scripts/font_tools/Generate-HASP-Fonts.ps1`. The editor's own text levels are unrelated: [Visual foundations → Text sizes](frontend-visuals.md#text-sizes).
The one exception is `nextion/fonts/repair_body.zi` (h24) and `repair_title.zi` (h72): subset `iso-8859-1` faces holding only what the repair page draws, used by the two repair projects and by no release HMI. They are why those files are 465 KB instead of the 1.2 MB the full Roboto faces gave them — see [The repair TFTs](nextion-editor.md#the-repair-tfts).

### Fitting text

`haui/utils/text.py` wraps text with the fonts' real glyph widths, exported to `haui/mapping/font_metrics.json` by `python -m scripts.hmi_layout.gen_virtual_layout`.

| Helper | Effect |
|--------|--------|
| `TextBox(width, height, border, max_len)` | drawing area of a text widget, from its `w`, `h`, `borderw` and `txt_maxl` |
| `text_width(text, font)` | width in px; a character without a text glyph counts as wide as the line is high |
| `fit_text(text, font, box)` | wraps into `width - 2 * border` and splits into pages of `(height - 2 * border) // line_height` lines, at most `max_len` stored bytes, keeping `\n` |
| `fits_line(text, font, box)`, `fit_line(candidates, font, box)` | single-line check, first candidate that fits |
| `has_glyphs(text, font)` | whether the font draws every character (icons start at U+E000) |

- The hub wraps, the display never re-wraps: every line it sends fits the box by glyph width, and the border stays clear on all sides because the display's inset is undocumented.
- A page's `_TEXT_BOXES` must match its HMI widgets — `haui/page/notify.py` holds one box per text widget and orientation. A mismatch fits the text to the wrong area.
- `font_metrics.json` is a generated asset: re-run `gen_virtual_layout` after a font or text-box change instead of editing it.

## Icons

An icon is a single glyph character written into a text widget. `haui/utils/icon.py` resolves the name (`get_icon("mdi:lightbulb")`) and rewrites `mdi:` / `hass:` names inside a text template; `ICON_MAPPING` and the per-domain mappings in `haui/mapping/icon_mapping.py` pick the default icon of an entity or item type; `haui/mapping/icons.py` holds the `ICO_*` constants pages use.

| Concern | Rule |
|---------|------|
| Finding one | Browse the [Icons Cheatsheet](../user/icons.md); the source character is on [Pictogrammers](https://pictogrammers.com/library/mdi/) |
| Colour | The glyph takes the text widget's foreground colour, so it is a theme role (`entity_on`, `entity_off`, `header_accent` in the header) or a colour the page sends — an icon never carries a colour of its own |
| Size | One glyph is as tall as the font it is drawn in, so the widget's font ID is the icon size |
| Previews | The editor and card previews read the generated `frontend/virtual/icon_map.json` (glyph → MDI name) |
| Adding one | Generate the font with `scripts/font_tools/` (Windows, `ZiLib.dll`), import the `.zi` into both projects, then use the name; `make generated-check` fails while `docs/cheatsheet.html` is stale |

## Themes and colors

Themes are semantic colour roles. The library is shared by all devices of one config entry (`ThemeLibrary`); a device selects a theme with `theme_id` (default `dark`), and a panel may set its own `theme_id` — an empty one follows the device theme (`HAUIPanel.theme`). Colours are edited on the shared theme in the editor's [Themes](../user/editor/themes.md) page, never per device; panel and item colours stay explicit overrides that applying a theme leaves untouched.

`BUILTIN_THEMES` in `haui/mapping/color.py` holds the neutral Dark, Light, White and Black plus Midnight, Ocean, Forest, Sunset, Violet and Sky. A new theme is one override dict over `COLORS`, so every role stays defined; `tests/test_color.py` requires each colourful theme's foregrounds to reach WCAG AA on its own background. A theme with a light page needs a light header and a dark `header_text`: `header_text` is also the default body text colour (`FunctionButtonMixin`), so a dark header leaves row names and notification texts white on a light page.

### How a theme reaches the display

1. Before every page switch the hub writes the theme globals declared in `Program.s`: `thmBg`, `thmHdrBg`, `thmHdrTxt`, `thmPressed`, `thmCompBg` (defaults = the `COLORS` palette).
2. The page's `Preinitialize` event assigns those globals to its own `bco` and `bco2`, its header, its slider tracks and every widget compiled with a theme colour, so an overridden colour shows from the first frame. The code is generated per page and pasted after `sendme` in both HMIs:

   ```bash
   python -m scripts.hmi_layout.gen_virtual_layout --theme-code grid
   ```

   Re-paste it whenever a widget compiled with a theme colour is added, removed or recoloured; `gen_virtual_layout --check` fails while a page's code is missing or stale. Never hand-edit generated theme code.
3. The body widgets' foregrounds are the second half of the same code, and it ships with a TFT: an HMI whose `Program.s` also declares the four `FOREGROUND_GLOBALS` globals (`thmCompTxt`, `thmActive`, `thmActiveDk`, `thmTxt`, defaults = the same palette) gets one `<widget>.pco=<global>` line per body widget, so the page paints those colours itself and the hub stops sending them. Until an HMI declares them, the code it demands is backgrounds only and the hub sends the foregrounds from `haui/mapping/theme_foregrounds.py` with the panel's first render, ahead of the page's own state and settings colours.

   `declares_foregrounds()` is the switch, so a half-finished migration fails the check instead of shipping a page that paints half a theme. Why it is worth a TFT: the foregrounds are one serial command per body widget today, and the row page has 35 of them, so opening that panel costs 40 display commands (about 80 ms at the 2 ms command spacing) instead of 9 (about 18 ms). Painting ten palettes as literals was considered and rejected: at ~90 assignments per palette and page, the code of one page alone would be ~900 lines, and the display compiles that code into every page.

   !!! note "Shipping it"
       Four steps, in this order, and the check guards every one of them: declare the four globals in both `Program.s` files, paste `--theme-code` into both HMIs (it prints the foreground lines from then on), compile both TFTs and advance `tft_version`, then stop sending `THEME_FOREGROUNDS` and delete the generated table.

!!! warning "A solid page paints its theme in Preinitialize, never afterwards"
    The hub writes `THEME_GLOBALS` to `Program.s` only before `goto_page`. A theme colour sent to a page that is already shown repaints part of a live screen, so the page must take its colours from the globals while it loads.

### Colour roles

The default dark palette (`COLORS` in `haui/mapping/color.py`; role keys in parentheses) steps up in brightness from the page to the header to the cards to a pressed card, on greys divisible by 8 so the display's 5/6/5-bit colour renders them neutral.

| Role | Used for | RGB | RGB565 |
|------|----------|-----|--------|
| `background` | page fill and every solid text-bearing widget | `#101010` / [16, 16, 16] | 4226 |
| `header_background` | the header bar | `#181818` / [24, 24, 24] | 6339 |
| `text` | body text | `#e0e0e0` / [224, 224, 224] | 59164 |
| `text_inactive`, `entity_unavailable` | inactive text, unavailable entity | `#737373` / [115, 115, 115] | 29582 |
| `text_disabled`, `component_pressed` | disabled text, every button's pressed state (`bco2`) and a dual-state button's highlighted tile | `#313131` / [49, 49, 49] | 12678 |
| `component_text`, `header_text` | widget text, header text | `#ffffff` / [255, 255, 255] | 65535 |
| `component_active` | button text action, active slider | `#4aa5ee` / [74, 165, 238] | 19773 |
| `component_active_dark` | dimmed active controls | `#3b86c3` / [59, 134, 195] | 15416 |
| `component_accent`, `header_accent` | accents, header icons | `#f69d31` / [246, 157, 49] | 62694 |
| `component_background` | slider tracks and the empty part of a progress bar | `#282828` / [40, 40, 40] | 10565 |
| `entity_on` | entity is on, and a grid tile whose item is on: the tile background is this colour mixed 16 % into the page background (`active_tile_color()`), and the power button is drawn in it | `#fdd835` / [253, 216, 53] | 65222 |
| `entity_off` | entity is off | `#44739e` / [68, 115, 158] | 17299 |

Both TFTs compile every solid widget on a content page with `background`, and only the header bar keeps `header_background`. Text-bearing widgets (tiles, row names and icons, select and notify buttons, keypad keys) use `background`, never `component_background`, so they stay flat on the page; `component_background` compiles at [49, 49, 49] and the hub repaints it when it shows the control.

### Backgrounds and contrast

Each decorative background of Clock, Weather and Clock Two has an explicit light/dark contrast variant that drives text, cycle cards and state icons together, not icons alone. The **Background** option (`background_option()` in `haui/page/clock_common.py`) names a picture the TFT embeds, the dark fill by default; `BACKGROUND_VARIANTS` in `haui/mapping/background.py` pairs each picture with its variant, and a value that names no picture falls back to the panel's theme contrast (`Theme.background_variant()`). Add a variant whenever a background is added.

Those pages set `USE_SYSTEM_COLORS = False`, so `HAUIPage.get_color()` returns the variant's palette (`Theme.get_background_color()`) instead of the selected theme: the picture, not the theme, decides what is readable. `background_commands()` resolves the panel's choice to a picture id before every page switch, so a value the display cannot paint — an empty field, a template that renders nothing, an unknown name, a `scheme` from an older version — falls back to the theme's picture instead of leaving the previous panel's picture on screen.

??? note "Why those pages paint a picture instead of the theme colour"
    A Nextion page's fill type is compiled, and the panel's Enhanced-series display offers only crop image, solid colour, image and no background; transparent fills belong to the Intelligent and Edge series, and *no background* shows the previous page. A picture cannot stand in for transparency either: this series converts the transparent pixels of an imported picture to the editor's *Transparent color replacement value* (black by default), so an RGBA PNG arrives as one flat colour. `aph` (opacity) is inert too: `sta` never takes `3` in either HMI, every widget's `aph` sits at its default `127`, and the pages draw opaque (`frontend/virtual/nextion-view.js` models the `sta` values as the display draws them). The letters, dots and cycles of those pages are crop-image widgets that pull their pixels from the same full-screen picture as the page, so they follow `system.vBackground` and nothing else. Painting the `background` role there needs a solid-fill duplicate of each page or one flat picture per theme colour — Nextion Editor work on the HMIs and the TFTs. Until then a theme names a picture: `theme` draws the theme's picture, and those pages follow it.

## Header

The header carries two function buttons on the left, two on the right and the title between them, across the top 50 px. Use outlined icons in `component_accent` (`header_accent` on the header bar) and another colour only where a state needs it.

| Widget | Geometry |
|--------|----------|
| `tHeader` | full width, 50 px tall: the header bar |
| `tTitle` | full width, on top of the bar |
| `bFncLPri`, `bFncLSec` | 50 × 50 px at the left end |
| `bFncRSec`, `bFncRPri` | 50 × 50 px at the right end |

## Adding a panel

A panel type is a physical page in both HMIs, a page class with a `COMPONENTS` registry and a `DESCRIPTOR`, one entry in the panel mapping, a sample for the previews and a user doc page. `custom_components/nspanel_haui/haui/page/light.py` is the reference implementation: an item option, base components merged into `COMPONENTS`, a render hook and a popup.

1. **Draw the page in both HMIs.** Add it to `nextion/nspanel_haui.HMI` with a unique page id and a page name, then mirror it in `nextion/nspanel_haui_portrait.HMI` with the same widgets, names, ids and event code ([adding a widget or a page](nextion-editor.md#adding-a-widget-or-a-page)). Send `sendme` in `Preinitialize`, paste the page's theme code after it on a solid-colour page, and enable `Send Component ID` on every widget the hub must react to.
2. **Dump both HMIs** to map widgets to components. `-d` clears the output folder, `-s` writes a stats summary, `-p visual` adds position, size and colours, and `build/` is git-ignored:

   ```bash
   python -m scripts.nextion2text.Nextion2Text -i nextion/nspanel_haui.HMI -o build/nextion-out/landscape -d -s -p visual
   python -m scripts.nextion2text.Nextion2Text -i nextion/nspanel_haui_portrait.HMI -o build/nextion-out/portrait -d -s -p visual
   ```

3. **Write the page class** `custom_components/nspanel_haui/haui/page/<type>.py`.
4. **Register it** in `_page_classes` in `custom_components/nspanel_haui/haui/mapping/panel.py`.
5. **Give it a preview sample** in `scripts/preview_gallery/sample_world.py` and check the coverage.
6. **Document it** in `docs/user/panels/panel_<type>.md` and in the overview table of `docs/user/panels/README.md`.
7. **Extract translations** after any new `_()`, `self.translate()` or `t()` call.
8. **Compile both TFTs** and advance `tft_version` ([after any HMI change](nextion-editor.md#after-any-hmi-change)).
9. **Run the gates**: `make hmi-check` (layouts, generated assets, preview coverage), `pytest tests/`, `node --test 'tests/frontend/*.test.mjs'`, `ruff check custom_components/ scripts/`, `mypy`.

### What the page class needs

| Part | Requirement |
|------|-------------|
| `COMPONENTS` | `HAUIPage.COMPONENTS.merge(...)` (or a standalone `ComponentRegistry(...)`) with one snake_case purpose name per widget, e.g. `title=Component(2, "tTitle")`. The id and name must match the HMI of **both** orientations |
| `DESCRIPTOR` | `PageDescriptor(type_key=..., page_name=..., page_id=..., label=_("..."), description=_("..."), category=..., icon=...)`; `page_id` is the physical Nextion page id, `category` a key of `PANEL_CATEGORIES` |
| Options | One `PageOption` per panel setting (`key`, `kind`, `default`, `label`, `description`, `section`), read with `self.option(panel, key)` in `start_panel()` |
| Hooks | `prepare()` for per-panel attribute defaults, `start_panel()` for callbacks and options, `render_panel()` for display commands, `_stop_panel()` for cleanup (never call `super()` there). Hook order: [Hub → panel](hub.md#panel) |
| Popup variant | `popup_alias_for="<parent type_key>"` for a different class on the same page, or `can_show_popup=True`. Nothing else to register |

Only `page_id` makes the preview work: the editor's panel cards are the hub's own render replayed in the Nextion simulator, so there is nothing to write for a new type. A popup that only opens with context (a notification, choices, a panel to unlock) gets its sample in `web/preview/virtual_panel.py`, never on the page.

### Preview and screens

`tests/test_card_renders.py` renders every panel type on the hub and replays the result in the simulator, so a page the simulator cannot draw from the hub's output fails the suite. A sample entity must advertise the features its page gates controls on — `supported_features` on a media player or vacuum decides which buttons the card shows.

```bash
pytest tests/test_card_renders.py
python -m scripts.preview_gallery.gen_preview_gallery --serve   # or --png
python -m scripts.check_preview_coverage
```

Every exposed panel — user types, system panels, popup aliases — must resolve to a physical page in both generated layouts. The same samples make up the [Screens overview](../user/screens.md): `gen_preview_gallery --docs` writes one PNG per card and orientation to `docs/assets/screens/` and to `docs/screens.html`, and the pull request that changes what a screen draws commits them, so never add a screenshot by hand.

### What a page doc must answer

A page in `docs/user/panels/` is the only place a user learns what a panel does. Answer, in this order:

- **About** — what the panel shows and which entity or item it belongs to.
- **How to configure** — every option from the `DESCRIPTOR`, with its default and what changing it does.
- **Controls** — what each widget displays and what touching it does, gestures included.
- **How it behaves** — what an unavailable, unknown or unsupported entity shows.
- **Popup** — with `can_show_popup`, when the popup opens and what it offers.

### Translations

```bash
python -m scripts.translations.extract_translations
```

The script scans the Python and JavaScript sources for string-literal `t()`, `host._t()`, `self.translate()` and `_()` calls, adds missing keys to every `haui/locale/*.json` (English text in `en.json`, an empty string elsewhere), removes keys nothing references, and prints what changed per language. Fill in the empty values and commit the locale files with the code.
