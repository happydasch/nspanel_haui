# Release process

`dev` is the integration branch and the repository default; `master` holds stable code
only. Day-to-day work is committed to `dev`, directly or as a pull request whose six
always-running checks are green. A stable release is a `dev` → `master` promotion pull
request that the `Protect master` ruleset gates, plus a `vX.Y.Z` tag on the merge commit,
which `release.yml` turns into the published release; afterwards `master` is merged back
into `dev`, so the two branches converge and the next cycle starts even. **No release
workflow pushes to `master`**: the stable workflow only publishes a tag on the promotion
merge; the development workflow alone commits one version bump to `dev` and dispatches
CI, so the branch manifest, the release tag and the image stay in step.

## What a release ships

| Asset | Built from | Published by | Consumed by |
|-------|------------|--------------|-------------|
| `nspanel_haui.bin` | `esphome/nspanel_haui_universal.yaml` compiled by `scripts/release/compile_firmware.sh` (the factory image) | `release.yml` for a stable tag, `dev-firmware.yml` for a dev build | serial/factory flashing; the same image serves every panel |
| `nspanel_haui_ota.bin` | the same build (its app image) | the same two workflows | the **HAUI Firmware** update entity, which installs it over HTTP OTA |
| `firmware-manifest.json` | `scripts/release/generate_firmware_manifest.py` | the same two workflows | ESPHome web-tools and the hub: version, OTA URL and md5, `variant`, `tft.version`, `tft.assets.eu` / `.us` |
| `nspanel_haui.tft` | `nextion/nspanel_haui.HMI`, compiled in the Nextion Editor | both workflows attach the committed file | landscape panels (`display_model: eu`) |
| `nspanel_haui_portrait.tft` | `nextion/nspanel_haui_portrait.HMI`, generated by `scripts/hmi_layout/gen_layout.py --spec portrait` and compiled in the Nextion Editor | both workflows attach the committed file | `display_model: us` panels |
| Integration source and zip | `custom_components/nspanel_haui/` at the tag | `release.yml` creates the release, `dev-firmware.yml` the prerelease | HACS/Marketplace installs; Home Assistant and the hub read the version from `manifest.json` |
| Release notes | `.github/release-notes/<tag>.md`, otherwise a pointer to `CHANGELOG.md` | `release.yml`; dev notes are written by the workflow | the body of the GitHub release |
| Screen overview (`docs/screens.html`, `docs/assets/screens/`) | `scripts/preview_gallery/gen_preview_gallery.py --docs` | a pull request that changes what a screen draws | the screen gallery of the docs site |

The five attached asset names are a frozen contract: `nspanel_haui.bin`, `nspanel_haui_ota.bin`, `firmware-manifest.json`, `nspanel_haui.tft` and `nspanel_haui_portrait.tft`. Renaming one breaks automatic updates for already-flashed panels; adding a variant is safe while the existing names stay unchanged. Both TFTs boot the display at 921600; the firmware starts its UART at the same rate and scans down only for an older TFT, so the two sides realign after every TFT upload.

The universal image needs no per-device build: `name_add_mac_suffix: true` appends the last six MAC digits at runtime, so every panel draws a unique hostname, mDNS name and setup access point from the same `.bin`. A build with your own credentials comes from `esphome/install.yaml` and the git-ignored `esphome/secrets.yaml` instead ([ESPHome Component](esphome.md#installation)).

`haui/controller/update.py` installs the TFT the firmware reports as `tft_required_version`, resolved through the manifest's `tft.assets` entry for the device's `display_model` (an unknown model resolves to `eu`). It reads the manifest from the latest release by default. The manifest names `"variant": "universal"`, and the hub installs only a manifest whose variant equals the one the device reports (`custom` for `install.yaml` and `esphome/nspanel_haui_dev.yaml` builds). A missing variant on either side fails closed, so a custom build is never flashed the universal image.

### How a panel picks the artifacts

| Update channel | Manifest it follows | Firmware variant |
|----------------|---------------------|------------------|
| **Stable** (default) | `releases/latest/download/firmware-manifest.json` of the latest stable release | `universal` |
| **Development** | the newest release in the cached GitHub release list that ships a manifest, dev prereleases included | `universal` |
| **Custom manifest URL** | the URL set under **Update settings → Advanced**, which overrides the channel | whatever the build embeds |

The **HAUI Firmware** and **HAUI Display** entities install from the selected manifest; the settings and the install order are in [Update Process](update-process.md#settings). When the selected manifest does not carry the TFT an installed firmware requires, the hub also reads the manifest of the release named like that firmware's version, and uses it only when firmware version and required TFT version match (the build variant is not compared, because a release ships one universal image but a TFT that serves both variants).

Outside the channels, both actions install one panel directly: `nspanel_haui.update_firmware` with `url` (an OTA image) or `version` (another release, older ones included), and `nspanel_haui.update_tft` with `url` or `version`. A local manifest written by `scripts/dev_release.py` carries no `tft` block, so a panel following a **Custom manifest URL** keeps its display unless you install one of these.

## Versioning and tags

Semantic Versioning, and every version string the tooling writes must parse as PEP 440. A `-` separator is unparseable (`0.4.5-dev1`) and the hub withholds the update, so use a dot: `0.4.5.dev1`.

| File | Holds | Written by |
|------|-------|------------|
| `custom_components/nspanel_haui/manifest.json` | the integration version, source of truth (`haui/version.py.get_integration_version()` reads it; a stable tag must equal it) | `python -m scripts.bump_version X.Y.Z` |
| `pyproject.toml` | packaging mirror | the same bump, stable versions only |
| `esphome/nspanel_haui/version.yaml` | `yaml_version` (must equal the manifest) and `tft_version` (the display image the firmware requires) | the same bump; `tft_version` only with `--tft-update` |
| `nextion/nspanel_haui.HMI`, `nextion/nspanel_haui_portrait.HMI` | global `system.tftVersion` | `--tft-update` for a same-length version; otherwise the Nextion Editor |
| `nextion/nspanel_haui.tft`, `nextion/nspanel_haui_portrait.tft` | the embedded `system.tftVersion` | recompiled in the Nextion Editor |

- `yaml_version` and `tft_version` are independent serials. The firmware reports the latter as `tft_required_version`, so a display fix can require a newer TFT than the firmware it ships with. Never rewrite the TFT version to match the firmware version.
- `hub_api_version` is a third, separate number (currently `1.0`, in `esphome/nspanel_haui/version.yaml` and `haui/version.py`). It describes the handshake and event contract, and only an incompatible change to either bumps its major part.
- A TFT change committed under an unchanged `tft_version` never reaches a panel that already reports that version. `scripts/verify_nextion/check_hmi_bump.py` fails the `tests (3.14)` job when an HMI or a TFT changed against the PR base and `tft_version` did not advance.
- Stable tags are `vX.Y.Z`, and the prepared notes file is named after the tag. `release.yml` fires on any `v*` tag and its preflight refuses one whose commit is not reachable from `master`, so a tag on a development commit can never become the latest stable release. A manual dispatch works only on a `v*` ref.
- `scripts/bump_version.py --check` (`make version-check`) fails on drift between these files. Never edit a version file by hand.
- Never push a tag to test firmware. Every `v*` tag becomes the *latest* release, which every panel with `firmware_auto_update` follows; test a build by dispatching **Development Firmware** and following it with a **Custom manifest URL** or the **Development** channel instead.

A TFT change that lands under no release needs its own bump before the next build, because a panel never installs an image whose version it already reports: run `python -m scripts.bump_tft_version --version X.Y.Z` (same-length versions only), set `tft_version` to the same value, recompile both TFTs in the Nextion Editor, and commit HMI, TFT and `version.yaml` together.

## Published development firmware

Dispatch **Actions → Development Firmware → Run workflow** on `dev`. The build takes the run number as a PEP 440 dev version, writes it into `manifest.json` and `version.yaml`, compiles the universal image, commits that bump to `dev`, tags the commit, publishes it as a prerelease and prunes the older ones:

```text
base version   the newest vX.Y.Z tag as its next patch, or the `base` input (0.6.0)
version        X.Y.(Z+1).dev<run>, one string for branch, image, tag and manifest
verified       the compiled OTA reports that version before anything is published
committed      one bot commit on dev: manifest.json + version.yaml
published      prerelease, not marked latest, both firmware images + both TFTs + manifest
pruned         all but the newest 10 X.Y.Z.devN prereleases, so the latest stable
               release never leaves the Marketplace's or the hub's release lists
```

A minor or major cycle passes its base explicitly (`base: 0.6.0`); a patch cycle needs no step, because the first build takes the released version's next patch. The workflow is dispatch-only on `dev`, so the image carries the development code; a dispatch queues behind a running build rather than cancelling it.

The bot commit is what makes a branch install work: the integration installed from `dev` (or from the tagged source) reports the same version as the firmware, and the hub finds the release's TFT manifest by that version. `pyproject.toml` and `tft_version` keep their released values until the stable prep, which moves them with the release.

A panel follows the channel through its **Update channel**: **Development** reads the cached GitHub release list and follows the `firmware-manifest.json` of the newest release in it that ships one, dev prereleases included; a stable release of the same version supersedes its dev builds. There is no fixed dev manifest URL. The CI image is `universal`, so it cannot replace firmware reporting `firmware_variant: custom`.

Because the development build versions the branch, an integration installed from `dev` reports the dev version; a panel that only switches its **Update channel** keeps the integration it has, usually the last stable release. That is deliberate: a development build never makes a stable version, and the stable promotion still moves `master` through its pull request and tag.

## Branches and cadence

| Branch | Role | Rules |
|--------|------|-------|
| `dev` | the integration branch, the repository's default branch | direct commits and merges are allowed; `ci.yml` runs on every push and on pull requests to it, nothing is required |
| `master` | stable code, docs at the site root | the "Protect master (release-only)" ruleset blocks direct and force pushes and branch deletion, and needs a pull request with the six always-running checks green |
| Feature and fix branches | one change, when a pull request is wanted | cut from `dev`, PR with `--base dev`, merged with a merge commit |
| `release/X.Y.Z` | release prep: version bump, changelog, notes, TFTs | cut from `dev`, PR with `--base dev`, merged with a merge commit |
| `hotfix/X.Y.Z` | a fix for a released version | cut from `master`, PR with `--base master`, merged, tagged, then merged back into `dev` |

The cycle: commit to `dev` → six checks green → promote `dev` into `master` with a pull request → checks green → merge with a merge commit → tag `vX.Y.Z` on that merge commit → `release.yml` publishes → merge `master` back into `dev`. Only the promotion and the following sync touch `master`; nothing else is a bot commit, and no workflow pushes a branch.

No fixed calendar. Patch releases close regressions and gate failures; minor releases ship features and breaking changes. A breaking change ships a `docs/user/update.md` entry and a CHANGELOG *Breaking changes* section — no alias is kept, so the upgrade guide is the only migration path.

Commits and PR titles use [Conventional Commits](https://www.conventionalcommits.org/) (`type(scope): message`, 100 characters at most, checked by the `Validate title` job). Fill in `.github/pull_request_template.md` with what changed, why, how it was tested and which device checks stayed unverified.

## CI gates and local checks

| Job | Workflow | Trigger | Proves |
|-----|----------|---------|--------|
| `tests (3.14)` | `ci.yml` | push and PR to `dev` and `master`; manual dispatch | icon cheatsheet and translations current (`make generated-check`), version sources agree (`make version-check`), the TFT bump gate, `pytest tests/` (card renders replayed through Node, the frontend style guard, both HMI layout checks, the display version check), `ruff format --check`, `ruff check`, `mypy` |
| `frontend` | `ci.yml` | the same | `npm run typecheck:frontend` and `node --test 'tests/frontend/*.test.mjs'` |
| `esphome` | `ci.yml` | the same | `esphome config esphome/nspanel_haui_universal.yaml` |
| `docs` | `ci.yml` | the same | `zensical build --strict`, and on a `master` push the site artifact for `deploy-docs` |
| `hassfest`, `hacs` | `ci.yml` | the same | Home Assistant integration and HACS repository validation |
| `deploy-docs` | `ci.yml` | push to `master`, manual dispatch on `master` — never a PR or `dev` | publishes Pages from the `docs-site` artifact |
| `Compile firmware` | `esphome-build.yml` | PRs touching `esphome/`, `requirements-esphome.txt`, `scripts/verify_firmware/`, the workflow or the setup action; manual, with the ESPHome channel | `make esphome-compile` and `make esphome-size`, which fails at 92 % of the app partition |
| `build` | `dev-firmware.yml` | manual dispatch on `dev` | the versioned universal prerelease, the manifest, and the prune of old dev releases |
| `release` | `release.yml` | `v*` tag push; manual dispatch on a `v*` ref | the tag commit is reachable from `master`, tag equals the `manifest.json` version, ESPHome compile, manifest generation (refuses a TFT that does not embed `tft_version`), prepared notes, asset upload; the run is never cancelled |
| `Validate title` | `pr-title.yml` | PR opened, edited, synchronized or reopened | Conventional Commits title, 100 characters at most |
| `Shell scripts` | `shellcheck.yml` | PRs and pushes touching a `*.sh` file | shellcheck over the scripts |

### Repository settings the release depends on

Three settings are prerequisites, not conveniences, and none of them is visible from the code:

- **`dev` is the default branch** and accepts direct pushes: development lands there, and only `master` is gated.
- **"Protect master (release-only)"** must keep the six status checks and stay free of bypass actors, so a promotion or hotfix reaches `master` only through a pull request whose checks ran.
- **"Allow GitHub Actions to create and approve pull requests"** may stay **off**: no workflow opens a pull request. Turn it on only if a future job needs to.

### Run the same gates locally

```bash
make -j4 check
```

That runs both test suites, `ruff format --check`, `ruff check`, `mypy`, `npm run typecheck:frontend`, the strict docs build, `make version-check` and `make generated-check` — everything push/PR CI checks except the ESPHome config. It needs the dev virtual environment plus the docs and frontend tooling; the ESPHome config lives in its own environment (`requirements-esphome.txt`, which conflicts with the dev one):

```bash
make hmi-check          # both HMI specs, generated layouts, preview coverage
make screens-check      # docs/screens.html and its PNGs against a fresh render (Chrome, Node 22+)
make esphome-config     # CONFIG defaults to esphome/nspanel_haui_universal.yaml
```

`make screens-check` reproduces the screen overview when a change alters what a panel draws; commit the regenerated files in that pull request. It stays out of `make check` because a screenshot's bytes belong to the browser that took them.

## Release runbook

### 1. Prepare

```bash
git switch dev && git pull
git switch -c release/0.5.6
python -m scripts.bump_version 0.5.6                      # firmware-only release
python -m scripts.bump_version 0.5.6 --tft-update         # release with a new TFT
python -m scripts.bump_version 0.5.6 --check --tft-update # dry run
```

Every run updates `manifest.json`, `pyproject.toml` and `yaml_version`; only `--tft-update` also writes ESPHome `tft_version` and both HMI `system.tftVersion` values, which is legal only for a same-length version — a length-changing bump needs the Nextion Editor. Recompile both TFTs after `--tft-update`. Merge the prep branch into `dev` (`gh pr create --base dev`, merge commit) so the promotion carries the bump.

### 2. Display assets, when the release carries them

```bash
python -m scripts.hmi_layout.gen_layout --spec portrait
# Nextion Editor: File → TFT file output → nextion/nspanel_haui_portrait.tft
python -m scripts.check_preview_coverage
python -m scripts.preview_gallery.gen_preview_gallery --docs
make hmi-check
```

### 3. Docs, notes and the changelog

1. Update the user docs for behaviour changes (install, actions, display models).
2. Write the `docs/user/update.md` entry and the CHANGELOG *Breaking changes* line for every breaking change.
3. Prepare `.github/release-notes/vX.Y.Z.md` with `## Before updating` and the `## Added` / `## Changed` / `## Fixed` sections the changelog carries, and give the top `## [Unreleased]` section its version and date.

| Document | Holds |
|----------|-------|
| `CHANGELOG.md` | the compact index: one line per change, grouped as *Breaking changes*, *Added*, *Changed* and *Fixed*, with the issue or PR link |
| `.github/release-notes/<tag>.md` | the detail for every changelog line: what the change does, why, what a user notices, what to do first |

Credit external contributors by their GitHub handle in both; keep repository-relative links (`docs/user/update.md#…`), which GitHub resolves against the tag.

### 4. Promote and tag

```bash
make -j4 check && make esphome-config
gh pr create --base master --head dev --title "chore(release): Promote X.Y.Z"
gh pr merge <n> --merge --body "Stable promotion for X.Y.Z"
```

Merge with a **merge commit**, so the history `dev` gathered lands on `master` and the tagged commit carries it. The promotion PR is the only way into `master`, and its `tests (3.14)` run is the report `release.yml` relies on. Never let a CI-skip marker reach that body or any commit message: GitHub scans the whole tagged message, skips the `v*` tag push and `release.yml` never starts. Recover with `gh workflow run release.yml --ref vX.Y.Z`.

Then tag the merge commit from a checkout of the canonical repository:

```bash
git switch master && git pull
git tag -a v0.5.6 -m "NSPanel HAUI 0.5.6"
git push origin v0.5.6
```

`release.yml` refuses a `v*` tag whose commit is not on `master`, so a tag pushed to a development commit fails its preflight instead of publishing.

### 5. Post-release

1. Merge `master` back into `dev`, so the two branches converge and the next cycle builds on the released code:

    ```bash
    git switch dev && git pull
    git merge --no-ff origin/master -m "chore: Merge master into dev"
    git push origin dev
    ```

2. Watch the `release` job; do not announce before it is green.
3. Check the five assets under the frozen names and that the body is the prepared notes:

    ```bash
    gh release view vX.Y.Z --json assets,body
    ```

4. Flash one panel from the published `.bin` and confirm the TFT auto-update.
5. Announce the release and link its notes.
6. Regenerate the screen overview in a follow-up pull request if the release changed it.

### 6. Rollback

Mark the GitHub release as a draft or delete it, then publish a patch release. Never re-point an existing tag at different bytes; a corrected tag with matching firmware and TFT versions is enough, because the hub installs only the TFT the firmware requires as `tft_required_version`.

```bash
gh release edit vX.Y.Z --draft     # withdraw it from the Marketplace and the panels
# then, from a fresh release/X.Y.(Z+1) branch cut from dev, the normal runbook
```

## Guardrails and known gaps

- **A tag push runs no `ci.yml`.** Only `release.yml` reacts to a tag, so tag only the promotion merge commit that was green on its pull request; the preflight refuses a tag that is not on `master`.
- **Release notes are a separate file.** Without `.github/release-notes/<tag>.md` the body is a pointer to the changelog, whose one-line entries carry no detail.
- **An Actions run that fails before its jobs start cannot be re-run.** Close and reopen the PR (or push a new head commit) once GitHub is healthy, then re-run the failed workflow. Check [githubstatus.com](https://www.githubstatus.com) before a release.
- **A failed docs deploy needs a new run, not a re-run.** When `deploy-docs` fails with `No artifacts named "github-pages"` ([actions/deploy-pages#451](https://github.com/actions/deploy-pages/issues/451)), a re-run uploads a second artifact and is refused; start a new run (`gh workflow run ci.yml --ref master`).
- **The Nextion Editor is GUI-only.** TFT compilation cannot be scripted, the version bump is scripted only for same-length versions, and the gate can only verify the result.
- **The portrait TFT derives from the landscape HMI.** Regenerate and recompile it after every landscape edit; a forgotten step ships a stale portrait or fails the gate.
- **Asset names are frozen.** Add variants without renaming existing assets.
- **~120 MB of Nextion binaries live in git** (`nextion/`: both HMIs, both TFTs, fonts and images), kept there so the HMI sources stay available to whoever rebuilds a TFT. They are marked `export-ignore` in `.gitattributes`, so GitHub's source archives — the zip HACS installs — carry none of them: an install or update downloads ~16 MB instead of ~74 MB. Raw URLs and release assets are unaffected, and a rewrite of the history would save little because git already delta-compresses successive HMI and TFT revisions. Do not move a file the integration reads into `nextion/`.
- **The universal image bakes a shared API key**, which also encrypts native OTA. The MAC suffix gives each device a unique name and access point, but the credentials are public: anyone on the LAN can reflash the panel. Use `install.yaml` with secrets for a private build.
- **The development channel is universal-only.** A panel running a `custom` build never receives a dev or stable CI image; rebuild it from `esphome/install.yaml` and serve it through its own manifest.
- **A dev build versions the branch, the tag and the firmware.** The dev workflow's one bot commit writes `manifest.json` and `version.yaml` on `dev`, then tags that commit; an integration installed from `dev` and custom firmware built from it report the same version and can find the release's TFT manifest. A panel that only follows the **Development** update channel keeps its installed integration.
- **ESPHome is pinned.** `min_version` in `esphome/nspanel_haui/base.yaml` and the pin in `requirements-esphome.txt` move together.
