# Release process

A release is cut from `dev` on a `release/X.Y.Z` branch, squash-merged into `master` and tagged there; `release.yml` then publishes the firmware images, both TFTs, the firmware manifest and the release notes as one GitHub release. This page lists what each artifact is, how the version and TFT serials relate, how the development channel differs, which CI jobs guard a change, and the order a maintainer runs the release steps in.

## What a release ships

| Asset | Built from | Published by | Consumed by |
|-------|------------|--------------|-------------|
| `nspanel_haui.bin` | `esphome/nspanel_haui_universal.yaml` compiled by `scripts/release/compile_firmware.sh` (the factory image) | `release.yml` for a stable tag, `dev-firmware.yml` for a dev build | serial/factory flashing; the same image serves EU and US panels |
| `nspanel_haui_ota.bin` | the same build (its app image) | the same two workflows | the **HAUI Firmware** update entity, which installs it over HTTP OTA |
| `firmware-manifest.json` | `scripts/release/generate_firmware_manifest.py` | the same two workflows | ESPHome web-tools and the hub: version, OTA URL and md5, `variant`, `tft.version`, `tft.assets.eu` / `.us` |
| `nspanel_haui.tft` | `nextion/nspanel_haui.HMI`, compiled in the Nextion Editor | both workflows attach the committed file | landscape panels (`display_model: eu`) |
| `nspanel_haui_portrait.tft` | `nextion/nspanel_haui_portrait.HMI`, generated by `scripts/hmi_layout/gen_layout.py --spec portrait` and compiled in the Nextion Editor | both workflows attach the committed file | `display_model: us` panels |
| Integration source and zip | `custom_components/nspanel_haui/` at the tag | `release.yml` creates the release, `dev-firmware.yml` the prerelease | HACS/Marketplace installs; Home Assistant and the hub read the version from `manifest.json` |
| Release notes | `.github/release-notes/<tag>.md`, otherwise a pointer to `CHANGELOG.md` | `release.yml`; dev notes from `scripts/release/dev_release_notes.py` | the body of the GitHub release |
| Screen overview (`docs/screens.html`, `docs/assets/screens/`) | `scripts/preview_gallery/gen_preview_gallery.py --docs` | `dev-firmware.yml` commits it, `deploy-docs` publishes it | the screen gallery of the `dev` docs |

The five attached asset names are a frozen contract: `nspanel_haui.bin`, `nspanel_haui_ota.bin`, `firmware-manifest.json`, `nspanel_haui.tft` and `nspanel_haui_portrait.tft`. Renaming one breaks automatic updates for already-flashed panels; adding a variant is safe while the existing names stay unchanged.

The universal image needs no per-device build: `name_add_mac_suffix: true` appends the last six MAC digits at runtime, so every panel draws a unique hostname, mDNS name and setup access point from the same `.bin`. A build with your own credentials comes from `esphome/install.yaml` and the git-ignored `esphome/secrets.yaml` instead ([ESPHome Component](esphome.md#installation)).

`haui/controller/update.py` installs the TFT the firmware reports as `tft_required_version`, resolved through the manifest's `tft.assets` entry for the device's `display_model` (an unknown model resolves to `eu`). It reads the manifest from the latest release by default. The manifest names `"variant": "universal"`, and the hub installs only a manifest whose variant equals the one the device reports (`custom` for `install.yaml` and `esphome/nspanel_haui_dev.yaml` builds). A missing variant on either side fails closed, so a custom build is never flashed the universal image.

### How a panel picks the artifacts

| Update channel | Manifest it follows | Firmware variant |
|----------------|---------------------|------------------|
| **Stable** (default) | `releases/latest/download/firmware-manifest.json` of the latest stable release | `universal` |
| **Development** | the newest release in the cached GitHub release list that ships a manifest, dev prereleases included | `universal` |
| **Custom manifest URL** | the URL set under **Update settings → Advanced**, which overrides the channel | whatever the build embeds |

The **HAUI Firmware** and **HAUI Display** entities install from the selected manifest; the settings and the install order are in [Update Process](update-process.md#settings). When the selected manifest does not carry the TFT an installed firmware requires, the hub also reads the manifest of the release named like that firmware's version, and uses it only when firmware version and required TFT version match (the build variant is not compared, because a release ships one universal image but a TFT that serves both variants).

Outside the channels, both services install one panel directly: `nspanel_haui.update_firmware` with `url` (an OTA image) or `version` (another release, older ones included) pauses the automatic firmware update until Home Assistant restarts, and `nspanel_haui.update_tft` with `url` or `version` installs a display image by hand. A local manifest written by `scripts/dev_release.py` carries no `tft` block, so a panel following a **Custom manifest URL** keeps its display unless you install one of these.

## Versioning and tags

Semantic Versioning, and every version string the tooling writes must parse as PEP 440. A `-` separator is unparseable (`0.4.5-dev1`) and the hub withholds the update, so use a dot: `0.4.5.dev1`.

| File | Holds | Written by |
|------|-------|------------|
| `custom_components/nspanel_haui/manifest.json` | the integration version, source of truth (`haui/version.py.get_integration_version()` reads it; a stable tag must equal it) | `python -m scripts.bump_version X.Y.Z` |
| `pyproject.toml` | packaging mirror | the same bump, stable versions only |
| `esphome/nspanel_haui/version.yaml` | `yaml_version` (must equal the manifest) and `tft_version` (the display image the firmware requires) | the same bump; `tft_version` only with `--tft-update` |
| `nextion/nspanel_haui.HMI`, `nextion/nspanel_haui_portrait.HMI` | global `system.tftVersion` | `--tft-update` for a same-length version; otherwise the Nextion Editor |
| `nextion/nspanel_haui.tft`, `nextion/nspanel_haui_portrait.tft` | the embedded `system.tftVersion` | recompiled in the Nextion Editor |

The bump advances these files per release kind:

| Release kind | Files the bump advances | `tft_version` |
|--------------|-------------------------|---------------|
| Stable, firmware only | `manifest.json`, `pyproject.toml`, `yaml_version` | unchanged |
| Stable with a display update | the same plus `tft_version` and both HMIs' `system.tftVersion` | new |
| Dev build (`dev-firmware.yml`) | `manifest.json`, `yaml_version`, and `tft_version` copied from the HMIs | copied |
| Local test build | nothing committed: pass `yaml_version` to `esphome` and write a manifest with `scripts/dev_release.py` | unchanged |

- `yaml_version` and `tft_version` are independent serials. The firmware reports the latter as `tft_required_version`, so a display fix can require a newer TFT than the firmware it ships with (firmware `0.4.5.dev29`, TFT `0.4.5.dev30`). Never rewrite the TFT version to match the firmware version.
- `hub_api_version` is a third, separate number (currently `1.0`, in `esphome/nspanel_haui/version.yaml` and `haui/version.py`). It describes the handshake and event contract, and only an incompatible change to either bumps its major part; the hub compares the major part and reports a mismatch instead of guessing at an unknown payload.
- A TFT change committed under an unchanged `tft_version` never reaches a panel that already reports that version. `scripts/verify_nextion/check_hmi_bump.py` fails the `tests (3.14)` job when an HMI or a TFT changed against the PR base or the pushed-from commit and `tft_version` did not advance.
- A firmware-only release keeps the previous TFT: bump without `--tft-update`, and the **HAUI Display** entity offers a TFT only to panels older than the shipped image.
- Stable tags are `vX.Y.Z`, and the prepared notes file is named after the tag. `release.yml` fires on any `v*` tag pushed anywhere, so cutting tags on green `master` commits is policy, not enforcement. A manual dispatch works only on a `v*` ref; a branch dispatch fails before the build.
- Dev tags are the bare version (`0.5.0.dev67`, never `v0.5.0.dev67`) and byte-identical to the manifest version: no `+local` and no `+g<sha>` segment. AwesomeVersion sorts a build segment above the final release it succeeds, so such a panel is never offered the release that supersedes it, and a leading `v` would start `release.yml` and mark a dev build *latest*.
- `scripts/bump_version.py --check` (`make version-check`) fails on drift between these files. Never edit a version file by hand, and never bump a dev version by hand: the workflow owns the `.dev<run>` suffix.
- During a dev cycle `pyproject.toml` keeps the last stable version while `manifest.json` carries `X.Y.Z.devN`, and `--check` ignores it there: a development version is a firmware-only bump that touches `manifest.json` and `yaml_version` alone.
- Never push a tag to test firmware. Every `v*` tag becomes the *latest* release, which every panel with `firmware_auto_update` follows; test a build through `scripts/dev_release.py` and a **Custom manifest URL** instead ([Update Process](update-process.md)).

A TFT change that lands on `dev` outside a release needs its own bump before the next build, because a panel never installs an image whose version it already reports:

1. Bump the HMI text with `python -m scripts.bump_tft_version --version 0.4.5.dev31` (same-length versions only; otherwise set `system.tftVersion` in both HMIs in the Nextion Editor).
2. Set `tft_version` in `esphome/nspanel_haui/version.yaml` to the same value.
3. Recompile both TFTs in the Nextion Editor and commit HMI, TFT and `version.yaml` together.

### Published development firmware

Dispatch **Actions → Development Firmware → Run workflow** on `dev`; its `guard` job refuses any other ref. Dispatch it when the change affects what a device installs — firmware or display inputs; hub-only, docs and frontend changes ride along in the next build.

1. `python -m scripts.release.dev_version <run number>` derives the version and writes it into `manifest.json` and `version.yaml`. A stable `X.Y.Z` in the manifest gives the base `X.Y.(Z+1)`; an existing `X.Y.Z.devN` keeps its base, so a minor cycle publishes `0.5.0.devN` builds. The run number is GitHub's repository-wide Actions counter, so a new cycle continues the global numbering (`0.5.0.dev55`, not `.dev1`) and every build stays unique and monotonic. It also copies `tft_version` from both HMIs' `system.tftVersion` and refuses to continue when the HMIs disagree, the version is not `X.Y.Z` or `X.Y.Z.devN`, or a TFT does not embed that version.
2. `bash scripts/release/compile_firmware.sh` compiles the universal image into `nspanel_haui.bin` and `nspanel_haui_ota.bin`.
3. `scripts/release/generate_firmware_manifest.py --tag <version>` writes the manifest with its `tft` block, and `scripts/release/dev_release_notes.py` the notes (build commit, the commits since the previous release tag, a changed-file summary).
4. `scripts/preview_gallery/gen_preview_gallery.py --docs` renders the screen overview.
5. One bot commit, `chore(release): development firmware <version>`, carries `manifest.json`, `version.yaml`, `docs/screens.html` and `docs/assets/screens/`. It is pushed to `dev` and tagged, so the Marketplace's source archive of the tag carries the dev version, and the branch keeps the released dev version instead of lagging on the last stable one.
6. The tag becomes a prerelease named `NSPanel HAUI 0.4.7.dev123 (abcdef1)` with both firmware images, both committed TFTs and `firmware-manifest.json`, not marked latest. The workflow retries the tag push up to five times; if it still fails, `dev` carries a version without a release and the next build publishes the next run number.
7. It deletes all but the newest 10 dev prereleases together with their tags, matching only `X.Y.Z.devN`, so they cannot push the latest stable release out of the release lists the Marketplace and the hub read — and a stable release can never be pruned.
8. The push uses `GITHUB_TOKEN`, which starts no workflow, so the run dispatches `ci.yml` on `dev`: that run tests the version commit and, as a dispatched run, deploys the docs with the new screens.

A `screens_only` dispatch skips the build, the version bump, the tag and the prerelease. It commits only the changed screens (`docs(screens): regenerate screen overview`) and dispatches `ci.yml` the same way to deploy them. The screens render at a fixed time, so the overview is byte-identical between runs and that commit appears only when a screen actually changed.

```bash
gh workflow run dev-firmware.yml --ref dev -f screens_only=true
```

A panel follows the channel through its **Update channel**: **Development** reads the GitHub release list (the cached list the release check uses, refreshed at most hourly) and follows the `firmware-manifest.json` of the newest release in it that ships one, dev prereleases included; a stable release of the same version supersedes its dev builds. There is no fixed dev manifest URL. The CI image is `universal`, so it cannot replace firmware reporting `firmware_variant: custom`.

Check each published dev release for `firmware-manifest.json`, both TFT assets and a manifest `tft.version` equal to the HMIs' `system.tftVersion`. The changelog entry and the prepared release notes are written for stable releases only.

!!! warning "Do not dispatch a development build during release prep"
    It pushes a bot commit onto `dev` at a moment you do not control once the release PR is open.

## Branches and cadence

| Branch | Role | Rules |
|--------|------|-------|
| `master` | release history and the repository's default branch; docs at the site root | receives `release/X.Y.Z` and hotfix PRs only; the "Protect master (release-only)" ruleset blocks direct and force pushes and branch deletion, needs a PR with the always-running checks green, and has no bypass actors |
| `dev` | integration branch and target of all day-to-day work; docs under `dev/` | not protected; takes direct pushes and PRs; dev firmware builds commit here |
| Feature branches | one change | cut from `dev`, PR base `dev` (`gh pr create --base dev`, because new PRs default to `master`) |
| `release/X.Y.Z` | release prep: version bump, changelog, notes, TFTs | cut from `dev`, squash-merged into `master` so one commit lands per release; no workflow commits to it |
| Hotfix branches | a patch that cannot wait for the next `dev` cycle | cut from `master`, PR into `master`, tag, then merge `master` back into `dev` |

The cycle: feature → PR into `dev` → `release/X.Y.Z` cut from `dev` → release prep there → squash-merge into `master` → tag → `release.yml` publishes → `master` merged back into `dev` → the next changelog section. Every tag is cut from a commit whose CI was green on its source branch.

Release prep stays on the release branch because a dispatched development build commits the next dev version to `dev`; a release PR taken straight from `dev` would no longer match the history it was reviewed on.

No fixed calendar. Patch releases close regressions and gate failures; minor releases ship features and breaking changes. A breaking change ships a `docs/user/update.md` entry and a CHANGELOG *Breaking changes* section — no alias is kept, so the upgrade guide is the only migration path.

Commits and PR titles use [Conventional Commits](https://www.conventionalcommits.org/) (`type(scope): message`, 100 characters at most, checked by the `Validate title` job), so the merged history reads like a changelog and the squash-merged release PR becomes the release commit. Fill in `.github/pull_request_template.md` with what changed, why, how it was tested and which device checks stayed unverified.

## CI gates and local checks

| Job | Workflow | Trigger | Proves |
|-----|----------|---------|--------|
| `tests (3.14)` | `ci.yml` | push and PR to `master` or `dev`; manual dispatch | icon cheatsheet and translations current (`make generated-check`), version sources agree (`make version-check`), the TFT bump gate, `pytest tests/` (card renders replayed through Node, the frontend style guard, both HMI layout checks, the display version check), `ruff format --check`, `ruff check`, `mypy` |
| `frontend` | `ci.yml` | the same | `npm run typecheck:frontend` and `node --test 'tests/frontend/*.test.mjs'` |
| `esphome` | `ci.yml` | the same | `esphome config esphome/nspanel_haui_universal.yaml` |
| `docs` | `ci.yml` | the same | `zensical build --strict`; on `dev` it first applies the dev site URLs (`scripts/docs/dev_site.sh`) and uploads the site as `docs-site` |
| `hassfest`, `hacs` | `ci.yml` | the same | Home Assistant integration and HACS repository validation |
| `deploy-docs` | `ci.yml` | push to `master` or `dev`, manual dispatch — never a PR | publishes Pages from the `docs-site` artifact plus a fresh build of the sibling branch: `master` at the root, `dev` under `dev/` |
| `Compile firmware` | `esphome-build.yml` | PRs touching `esphome/`, `requirements-esphome.txt`, `scripts/verify_firmware/`, the workflow or the setup action; manual, with the ESPHome channel `pinned`/`latest`/`dev` and the config universal or dev | `make esphome-compile` and `make esphome-size`, which fails at 92 % of the app partition; the build tree is not restored, so a stale incremental build cannot hide a compile error |
| `guard`, `build`, `screens`, `publish` | `dev-firmware.yml` | manual dispatch on `dev` only | the versioned universal prerelease, the single version commit on `dev`, the screen overview and the `ci.yml` dispatch (see [Published development firmware](#published-development-firmware)) |
| `release` | `release.yml` | `v*` tag push; manual dispatch on a `v*` ref | tag equals the `manifest.json` version, ESPHome compile, manifest generation (refuses a TFT that does not embed `tft_version`), prepared notes, asset upload; the run is never cancelled |
| `Validate title` | `pr-title.yml` | PR opened, edited, synchronized or reopened | Conventional Commits title, 100 characters at most |
| `Shell scripts` | `shellcheck.yml` | PRs and pushes touching a `*.sh` file | shellcheck over the scripts |

The tag-vs-manifest check and the asset upload run only in `release.yml`. `esphome-build.yml`, `release.yml` and `dev-firmware.yml` each compile the firmware for what they need, and push/PR CI never publishes. The HMI layout and display version checks run in push/PR CI only, so the tagged commit passed them on its release PR.

Concurrency differs per workflow and matters during a release: `ci.yml` cancels a superseded run on the same branch or PR, its docs deploy included, while `release.yml` and `dev-firmware.yml` never cancel a run in progress (a cancelled release can leave a partial release) and serialise on their own group.

### Run the same gates locally

```bash
make -j4 check
```

That runs both test suites, `ruff format --check`, `ruff check`, `mypy`, `npm run typecheck:frontend`, the strict docs build, `make version-check` and `make generated-check` — everything CI's push/PR jobs check except the ESPHome config. It needs the dev virtual environment plus the docs and frontend tooling; the ESPHome config lives in its own environment (`requirements-esphome.txt`, which conflicts with the dev one):

```bash
make hmi-check          # both HMI specs, generated layouts, preview coverage
make screens-check      # docs/screens.html and its PNGs against a fresh render (Chrome, Node 22+)
make esphome-config     # CONFIG defaults to esphome/nspanel_haui_universal.yaml
python -m scripts.verify_nextion.check_hmi_bump --base origin/master
```

`make screens-check` stays out of `check` because a screenshot's bytes belong to the browser that took them; `--strict` adds that byte comparison for the runner that writes them. A stale overview is fixed with `python -m scripts.preview_gallery.gen_preview_gallery --docs`, never by editing the generated files.

## Release runbook

Run the steps on the release branch. `make release-preflight` reports what a machine can answer — the version against the branch name, the version mirrors, the display TFT gate, the screen overview when a display input changed, and the notes file against the changelog section — as *passed*, *regenerate* (the command follows), *manual* or *failed*, and prints the steps that stay with a person. It never writes, builds or tags:

```bash
make release-preflight                  # report the machine-checkable items
make release-preflight ARGS=--draft      # also print a draft release body
make release-preflight ARGS=--strict     # also fail on a stale screen overview
make release-preflight ARGS=--skip-screens
```

### 1. Pre-flight

1. Confirm `dev` and `master` are green, and that the hardware passlist holds on real EU and US/portrait panels for any release that changes firmware or display behaviour.
2. Freeze features, decide the version number and collect the pending breaking changes.
3. Install the repository hooks once per clone (`scripts/git_hooks/install.sh`) so the virtual layouts are regenerated and portrait drift is caught before CI.
4. Run the gates on the candidate:

    ```bash
    make -j4 check
    make esphome-config
    gh run list --branch dev --limit 5
    gh run list --branch master --limit 5
    ```

### 2. Version bump

```bash
git switch dev && git pull
git switch -c release/0.5.0
python -m scripts.bump_version 0.5.0                      # firmware-only release
python -m scripts.bump_version 0.5.0 --tft-update         # release with a new TFT
python -m scripts.bump_version 0.5.0 --check --tft-update # dry run
```

Every run updates `manifest.json`, `pyproject.toml` and `yaml_version`; only `--tft-update` also writes ESPHome `tft_version` and both HMI `system.tftVersion` values. The script edits the HMI files in place, which is legal only for a same-length version (`0.4.2` → `0.4.3`); a length-changing bump needs the Nextion Editor. It never touches `CHANGELOG.md`. Recompile both TFTs after `--tft-update`: the gate verifies the committed files, it cannot prove they were rebuilt from the HMI.

### 3. Nextion assets

1. Open `nextion/nspanel_haui.HMI` in the Nextion Editor, make or verify the release's display changes, and compile **File → TFT file output** to `nextion/nspanel_haui.tft` — the procedure is in the [Nextion Editor guide](nextion-editor.md).
2. Close the Nextion project before a script touches an HMI file, then regenerate the portrait HMI, compile it and check the preview coverage:

    ```bash
    python -m scripts.hmi_layout.gen_layout --spec portrait
    # Nextion Editor: File → TFT file output → nextion/nspanel_haui_portrait.tft
    python -m scripts.check_preview_coverage
    make hmi-check
    ```

### 4. Docs and firmware

1. Update the user docs for behaviour changes (install, services, display models).
2. Write the `docs/user/update.md` entry and the CHANGELOG *Breaking changes* line for every breaking change.
3. Validate the docs and the firmware config on the candidate:

    ```bash
    make docs
    make esphome-config
    ```

### 5. Release notes and tagging

The changelog and the release notes split the work:

| Document | Holds |
|----------|-------|
| `CHANGELOG.md` | the compact index: one line per change (two at most), grouped as *Breaking changes*, *Added*, *Changed* and *Fixed*, in the user's terms, with the issue or PR link; a breaking change links its `docs/user/update.md` section |
| `.github/release-notes/<tag>.md` | the detail for every changelog line: what the change does, why it was needed, what a user notices; what to do before updating; known limits; the contributors and a compare link |

Credit external contributors by their GitHub handle in both and keep individual maintainer names out of the release body. Repository-relative links (`docs/user/update.md#…`) work in the release body, because GitHub resolves them against the tag.

1. Prepare `.github/release-notes/vX.Y.Z.md` on the release branch: `## Before updating` for the changelog's *Breaking changes*, and `## Added` / `## Changed` / `## Fixed` for the sections that carry entries (`make release-preflight` lists what is missing).
2. Write the `CHANGELOG.md` section by hand: heading with the release date and one line per change.
3. Open the PR into `master` and squash-merge it with a clean body:

    ```bash
    gh pr merge <n> --squash --body "Release prep for X.Y.Z"
    ```

    Never let `[skip ci]` reach that body or any commit message on this path: GitHub scans the whole tagged commit message, skips the `v*` tag push and `release.yml` never starts. Recover a skipped push with `gh workflow run release.yml --ref vX.Y.Z`.
4. Tag from a checkout of the canonical repository (`gh auth login` first). The command reads the version from `origin/master`, requires a successful push CI run for that commit, and never moves an existing tag or pushes a local branch:

    ```bash
    python -m scripts.release.publish_stable                 # preview version, commit and CI run
    python -m scripts.release.publish_stable --push vX.Y.Z   # confirm the tag printed above
    ```

5. Watch the `release.yml` run; do not announce before it is green.

### 6. Post-release

1. Check the release page for `nspanel_haui.bin`, `nspanel_haui_ota.bin`, both TFTs and `firmware-manifest.json` under the frozen names, and for the body showing the prepared notes:

    ```bash
    gh release view vX.Y.Z --json assets,body
    ```

2. Flash one panel from the published `.bin` and confirm the TFT auto-update.
3. Announce the release and link its notes.
4. Merge `master` back into `dev`, resolving the version files to the released version, and open the next changelog section:

    ```bash
    git switch dev && git pull --ff-only origin dev
    git merge origin/master   # resolve manifest.json and version.yaml to X.Y.Z
    git push origin dev
    ```

    Add `## [X.Y.(Z+1)] — unreleased` and its link reference to `CHANGELOG.md`.
5. Start a minor cycle with the bump script before the first dev build; a patch cycle needs no step, because the first build derives its version from the released one:

    ```bash
    python -m scripts.bump_version X.Y.0.dev0
    git commit -am "chore(release): start the X.Y.0 development cycle"
    git push origin dev
    ```

    `.dev0` is a placeholder until the first build writes its own run number; a real run number here could make that build's version commit empty.

### 7. Rollback

Mark the GitHub release as a draft or delete it, then publish a patch release. Never re-point an existing tag at different bytes; a corrected tag with matching firmware and TFT versions is enough, because the hub installs only the TFT the firmware requires as `tft_required_version`.

```bash
gh release edit vX.Y.Z --draft     # withdraw it from the Marketplace and the panels
# then, from a fresh release/X.Y.(Z+1) branch, the normal runbook
```

## Guardrails and known gaps

- **An Actions run that fails before its jobs start cannot be re-run.** Close and reopen the release PR (or push a new head commit) once GitHub is healthy, then re-run the failed workflow; the `master` ruleset needs `tests (3.14)`, `frontend`, `esphome`, `docs`, `hassfest` and `hacs` green. Check [githubstatus.com](https://www.githubstatus.com) before a release.
- **A failed docs deploy needs a new run, not a re-run.** When `deploy-docs` fails with `No artifacts named "github-pages"` ([actions/deploy-pages#451](https://github.com/actions/deploy-pages/issues/451)), a re-run uploads a second artifact and is refused; start a new run (`gh workflow run ci.yml --ref dev`) or let the next push deploy.
- **A tag push runs no `ci.yml`.** Only `release.yml` reacts to a tag, so tag only commits that were green on their source branch.
- **Release notes are a separate file.** Without `.github/release-notes/<tag>.md` the body is a pointer to the changelog, whose one-line entries carry no detail.
- **`publish_stable.py` refuses rather than guesses.** It exits when `origin` does not push to the canonical repository, when `origin/master` carries no stable version in `manifest.json`, when the tag already exists on the remote, when there is no successful `ci.yml` push run for that commit, or when `origin/master` moved since the preview — rerun the preview instead of forcing the push.
- **`make release-preflight` is read-only.** `dev-firmware.yml` stays the only writer of the screen overview, `release.yml` the only builder and publisher, and `publish_stable.py` the only tag push.
- **The Nextion Editor is GUI-only.** TFT compilation cannot be scripted, the version bump is scripted only for same-length versions, and the gate can only verify the result.
- **The portrait TFT derives from the landscape HMI.** Regenerate and recompile it after every landscape edit; a forgotten step ships a stale portrait or fails the gate.
- **Asset names are frozen.** Add variants without renaming existing assets.
- **~120 MB of Nextion binaries live in git** (`nextion/`: both HMIs, both TFTs, fonts and images). Marketplace downloads carry them, so repo and zip size grow with every TFT rebuild; they stay committed so the HMI sources remain available, and Git LFS or release-only storage is undecided.
- **The universal image bakes a shared API key**, which also encrypts native OTA. The MAC suffix gives each device a unique name and access point, but the credentials are public: anyone on the LAN can reflash the panel. Use `install.yaml` with secrets for a private build.
- **The development channel is universal-only.** A panel running a `custom` build never receives a dev or stable CI image; rebuild it from `esphome/install.yaml` and serve it through its own manifest.
- **ESPHome is pinned.** `min_version` in `esphome/nspanel_haui/base.yaml` and the pin in `requirements-esphome.txt` move together.
