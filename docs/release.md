# Release process & strategy

Audience: maintainers. This page documents how a release is cut today, what CI
enforces and the known risks of the setup. It is the single place to start when
preparing a release; the design rationale behind individual decisions stays in
[Development](development.md), and planned improvements are tracked in the
[Roadmap](https://github.com/happydasch/nspanel_haui/blob/master/ROADMAP.md#release-tooling).

## What a release ships

| Artifact | Source | Consumer |
|----------|--------|----------|
| Integration (Marketplace/zip) | `custom_components/nspanel_haui/` at the tag | Home Assistant users |
| `nspanel_haui.bin` | factory flash image compiled by CI from `esphome/nspanel_haui_universal.yaml` | manual/serial flashing; same binary for EU and US panels |
| `nspanel_haui_ota.bin` | OTA app image compiled by the same CI build | installed by the hub's `HAUI Firmware` update entity |
| `firmware-manifest.json` | generated by CI for `v*` tag pushes | ESPHome web-tools update schema; the hub reads it for the version, image URL, md5 and build `variant` |
| `nspanel_haui.tft` | `nextion/nspanel_haui.HMI`, compiled in Nextion Editor | landscape panels |
| `nspanel_haui_portrait.tft` | `nextion/nspanel_haui_portrait.HMI`, generated from the landscape HMI by `scripts/gen_portrait` | `display_model: us` panels |

The five attached asset names — `nspanel_haui.bin`, `nspanel_haui_ota.bin`,
`firmware-manifest.json`, `nspanel_haui.tft` and `nspanel_haui_portrait.tft` — are
a **frozen contract**. `haui/device_config.py` maps `display_model` to the TFT
filenames; `haui/controller/update.py` installs the TFT version the firmware
reports as `tft_required_version`, using the per-model asset in the manifest.
The hub reads `firmware-manifest.json` (by default through
`releases/latest/download/`) for the OTA image and its checksum.
Renaming an asset breaks automatic updates for
already-flashed panels, so a rename needs a migration story first. Adding a
variant (for example the high-speed TFT planned for v0.5) is safe as long as the
existing names stay unchanged; the update controller must map each device to the
right variant.

The release manifest carries `"variant": "universal"`: the image was compiled
from `esphome/nspanel_haui_universal.yaml` with the public credentials.  The hub
only offers/installs a manifest whose variant matches the one the device
reports (built-in `install.yaml` and dev builds report `custom`), so a custom
build is never flashed the universal image.  This is a **runtime contract
between the manifest and the device state** — the next generation of OTA images
must keep publishing a `variant`, and the device state must keep reporting it,
or the hub withholds the update (fail closed).

## Versioning and tag policy

Semantic Versioning. `custom_components/nspanel_haui/manifest.json` is the
source of truth; `haui/version.py` reads it at runtime. `scripts/bump_version.py`
updates firmware version sources every time; `--tft-update` additionally updates
the display version sources. A development version (`X.Y.Z.devN`, the
`.dev<run>` shape the dev-release CI publishes) is a firmware-only bump: it updates
`manifest.json` and the firmware `yaml_version` but leaves `pyproject.toml`,
`tft_version` and the HMI binaries at their stable values, because the dev
channel ships no display TFT:

1. `custom_components/nspanel_haui/manifest.json` — source of truth.
2. `pyproject.toml` — packaging mirror.
3. `esphome/nspanel_haui/version.yaml` — firmware `yaml_version`; its separate
   `tft_version` is advanced only when a TFT update ships.
4. The Nextion HMI files (`nextion/nspanel_haui.HMI` and
   `nextion/nspanel_haui_portrait.HMI`) — global `system.tftVersion`, updated
   with `--tft-update` and checked against the integration version by the
   release gate unless the unchanged TFT is explicitly pinned.

The bump script is a *version* bump only and never edits `CHANGELOG.md`. The
changelog (heading plus release date, and the "Breaking changes" section with
its `docs/upgrading.md` entry), and the prepared GitHub release notes in
`.github/release-notes/<tag>.md` are written by hand from the merged commits —
no tooling generates them.
`scripts/bump_version.py --check` is the dry run CI uses to fail on drift, and
`tests/test_bump_version.py` covers the script. The HMI edit is scripted only
for same-length versions (`0.4.2` → `0.4.3`); a length-changing bump needs the
Nextion Editor (see [step 2](#2-version-bump)).

**Shipping unchanged TFTs:** a release may keep the previous TFT binaries (a
hotfix whose display files did not change). Run `scripts/bump_version.py
<version>` without `--tft-update`: firmware `yaml_version` advances, while
`tft_version` and the HMI `system.tftVersion` stay at the embedded display
version. Set the repository variable `TFT_VERSION_PIN` to that version (for
example, `0.4.3`) so CI tolerates the HMI/integration version mismatch. The
release manifest gets its TFT version from `esphome/nspanel_haui/version.yaml`,
so the **HAUI Display** entity only offers the TFT when a panel is older than
the pinned image; a firmware-only release does not trigger an unnecessary TFT
install. Delete the variable again when a release bumps the TFTs.

**Tags:** use `vX.Y.Z`. The workflow itself is not branch-restricted: any
`v*` tag push starts `release.yml`, wherever it is pushed. That tags are only
ever cut on `master` is **policy**, not enforcement — keep tagging green
`master` commits. Manual dispatch re-runs the whole workflow for the selected
ref; only the version-vs-tag check and the `firmware-manifest.json` generation
are guarded on `v*` tags, so a dispatch on a branch still reaches the GitHub
release action and publishes a GitHub release for that ref — it is not a dev
preview. Older history is tagged without the prefix (`0.3.2`, `0.3.1`);
those tags never ran the automated workflow. Do not "fix" old tags — the
device-side lookup tolerates both forms.

**Never push a tag to test firmware.** Every `v*` tag becomes a regular
release, GitHub marks it *latest*, and every panel's **HAUI Firmware** entity
reads `releases/latest/download/firmware-manifest.json` — so all panels with
`firmware_auto_update` on install it. Use a
[local test release](#test-firmware-updates-with-a-local-release) instead.

Development firmware is now built and published on every successful push to
`dev`. The CI prerelease channel described below is separate from the local
workflow used for private/custom builds.

### Published development firmware

Every successful push to `dev` builds the CI-safe universal image and publishes a
GitHub prerelease whose tag is the release version. Its version is based on the
next patch release plus the workflow run number (for example, `0.4.5.dev123`), so
each successful push has a distinct update version. The release name adds the
short commit (`NSPanel HAUI 0.4.5.dev123 (abcdef1)`) and its notes link to the
build commit, enumerate commits included in that push, and list changed files.
Only the newest 10 dev prereleases are kept; the workflow deletes older ones
together with their tags, because the Home Assistant Marketplace (like HACS
before it) reads only the newest 30 releases and would otherwise lose the latest
stable release (a fresh install then falls back to the default branch, `dev`).

The version deliberately carries no `+g<sha>` build segment. Home Assistant and
its Marketplace compare versions with AwesomeVersion, which sorts
`0.4.5.dev16+g778f2ce` *above* the final `0.4.5` and above a later
`0.4.5.dev17`, so a build with that segment is never offered the release that
supersedes it. Builds published before 2026-11-04 carry the segment: a panel or
integration install on one of them needs one manual install of a newer build
(Marketplace: **Install another version**; panel: **Install firmware** with that
version), after which updates are offered normally.

The tag points at a small release commit that carries the version: the workflow
writes the dev version into `custom_components/nspanel_haui/manifest.json` (and
the firmware's `esphome/nspanel_haui/version.yaml`), commits those two files as
`chore(release): development firmware <version>` and tags that commit. The
Marketplace downloads the *source archive of the tag*, and Home Assistant and the
hub (`get_version()`) read the version from its manifest, so tagging the plain
branch commit would ship a dev build that calls itself the stable version. That
same versioned commit is pushed
back onto the `dev` branch (its `[skip ci]` trailer keeps GitHub from
re-triggering the workflow on that push), so the branch's tracked `version.yaml`
carries the released dev version instead of lagging on the last stable release.
As a consequence the tip of `dev` is always a bot `[skip ci]` commit, so release
prep happens on a `release/X.Y.Z` branch (see
[Branches and cadence](#branches-and-cadence)).
The next run derives the next dev version from that
`X.Y.Z.devN`: it keeps the same `X.Y.Z` base (no stable `X.Y.Z` has shipped yet)
and only advances the run number, and jumps to `X.Y.(Z+1).devN` again once the
master merge-back has returned `dev` to a stable manifest.
The tag push is retried a few times, because a GitHub Git Operations incident
can reject it (`remote: fatal error in commit_refs`) after the version commit
already reached `dev`. If it still fails, `dev` carries a version that has no
release. Nothing needs repairing: the next push to `dev` builds and publishes the
next run number.

The Marketplace reads release tags as *available* versions and records the tag
it installed as the *installed* one, so it can order dev releases and only offers a build
that is actually newer than the one installed. Both must be a valid PEP 440
version with no `-` separator: for an unparseable pair such as the old
`dev-<run>-<sha>` tags, it falls back to plain string inequality and keeps
offering the installed build as an update forever.

There is no fixed dev manifest URL. The hub's **dev** update channel reads the
GitHub release list (the same cached list its release check uses, refreshed at
most hourly or on a manual check) and follows the `firmware-manifest.json` of the
newest release in it, dev prereleases included. A stable release supersedes the
dev builds of its version.

Set a **universal test panel's** **Firmware update channel** to **dev** to
follow `dev`; leave it on **stable** on production panels. These CI images use
the documented public universal credentials and have `firmware_variant: universal`.
They are not compatible with devices running a private/custom build (`custom`):
keep building those from your own ESPHome config and use the local test-release
workflow below. Dev firmware publishes no display TFT (its manifest has no
`tft` block), so the **HAUI Display** entity offers no update and the display
keeps the last TFT installed on it; to test display changes, build/install a
TFT from a URL.

The prerelease notes show the exact commit and changed-file summary. Use the
commit link to inspect the full diff; the `CHANGELOG.md` entry and the prepared
release notes are written for stable releases only.

### Your custom firmware: choose `dev` or `master`

The published CI dev image is `universal`; it cannot replace firmware reporting
`firmware_variant: custom`. For your own panel, build the local custom config
from the branch you want to test, then use the local-manifest flow below. This
keeps your credentials and lets you compare branch builds without publishing a
custom image publicly.

1. Commit the changes you want included, then select and update the source
   branch. The build records `HEAD`, so do not build with uncommitted source
   changes if you want the version to identify exactly what was installed.

   ```bash
   git switch dev       # work in progress
   git pull --ff-only origin dev
   # Or choose the released source instead:
   # git switch master
   # git pull --ff-only origin master
   git status --short   # review the worktree before building
   git log -1 --oneline
   ```

   The repository's `esphome/secrets.yaml` is tracked with placeholders. If you
   put local credentials there for this build, keep them unstaged and never
   commit them; the file itself is tracked.

   `esphome/nspanel_haui_dev.yaml` builds the checked-out repository source with
   your local `esphome/secrets.yaml`. If you build through `esphome/install.yaml`
   instead, its `remote_package.ref` is `master` by default; change that local
   value to `dev` when testing `dev`, and back to `master` for the released
   source. Do not commit a machine-specific branch override.

2. Give every installed test build a higher prerelease number, and include both
   the source branch and short commit hash. For example, if `0.4.3` is the
   current stable release and `0.4.5` is next, use `dev1`, `dev2`, `dev3`, …
   across both branches (increment for every new build):

   ```bash
   SOURCE=dev                         # use master when building master
   BUILD=1                            # next unused number; keep increasing it
   SHA=$(git rev-parse --short HEAD)
   VERSION="0.4.5.dev${BUILD}+${SOURCE}.g${SHA}"
   esphome -s yaml_version "$VERSION" compile esphome/nspanel_haui_dev.yaml
   ```

   The version distinguishes `dev` from `master` and its hash points to the
   exact committed source (`git show <hash>`). The increasing `.devN` is
   important: the hub offers only a version newer than the one already
   installed. Do not reuse a number, even when switching branches. Replace
   `0.4.5` with the next planned stable version when the release line changes.
   The **HAUI Firmware** entity shows this as the installed version, making the
   branch, build order, and source commit visible in Home Assistant.

3. Follow the local-release steps below, passing this same `VERSION` to
   `scripts/dev_release.py` and `--variant custom`. Set the test panel's
   **Firmware manifest URL** to the local manifest. Keep display auto-install
   off unless you have also built and installed the matching TFT.

A custom build from an older `master` commit can have a lower version than the
`dev` build already installed. The update entity will not offer that downgrade;
use the direct URL install for an intentional return to an older build. The
normal release image/manifest remains `universal` and is not an OTA route for a
custom panel.

### Test firmware updates with a local release

`scripts/dev_release.py` turns a local build into the two files a release
carries for over-the-air updates, written to a folder Home Assistant serves
(`/config/www/…` is served as `/local/…`): `nspanel_haui_ota.bin` and
`firmware-manifest.json` (the schema the release workflow writes, with the
image URL and md5).

1. Build the test panel's firmware with a test `yaml_version`, either in its
   device YAML or on the command line. Use a **valid PEP 440 version**: the
   hub compares with the same rules as Home Assistant, and the development
   workflow validates its own builds the same way. Replace the `-` separator
   (`0.4.5-dev1` is not parseable and the hub would withhold the update) with a
   `.` (`0.4.5.dev1` is):

    ```bash
    esphome -s yaml_version 0.4.5.dev1 \
      compile esphome/nspanel_haui_universal.yaml
    ```

    `yaml_version` must equal the manifest version: the hub offers the
    manifest's firmware whenever its version is newer than the one the panel
    runs, so a build reporting an older version reinstalls forever. Each test
    release needs a newer one (`.dev1`, `.dev2`, …) because the hub only offers
    a newer version.

2. Write the test release:

    ```bash
    python scripts/dev_release.py \
      --image esphome/.esphome/build/nspanel-haui/build/firmware.ota.bin \
      --version 0.4.5.dev1 \
      --base-url http://homeassistant.local:8123/local/nspanel \
      --variant universal \
      --out /path/to/homeassistant/config/www/nspanel
    ```

    The script refuses a factory image, an image larger than the app partition,
    an image whose embedded `yaml_version` does not match, and a manifest
    variant different from the one embedded in the image. The example above
    builds the universal config, so pass `--variant universal`; custom builds
    from `install.yaml` or `nspanel_haui_dev.yaml` use the default `custom`.
    The written manifest carries no `tft` block, so the display keeps its
    current TFT; install a matching TFT from a URL when the display layout
    changed.

3. In the device editor's **Updates** section, set the test panel's
   **Firmware manifest URL** to the written manifest
   (`http://homeassistant.local:8123/local/nspanel/firmware-manifest.json`).
   The hub reads it as soon as the settings are saved, and the panel's
   **HAUI Firmware** entity offers each newer test release; the hub installs it
   automatically or with **Install** / **Device Manager → Install firmware**.
   Without the setting, the hub follows the configured channel and installs a
   newer release over the test build.

For a one-off build, skip the manifest: install the image with
`nspanel_haui.update_firmware` and `url` (this pauses the automatic firmware
update until Home Assistant restarts).

The hub treats the firmware's `tft_required_version` as the TFT it needs; this
is independent of `yaml_version` and remains pinned for firmware-only releases.
A test firmware can therefore use the current TFT without advertising it as a
GitHub TFT update. Dev manifests ship no TFT, so keep `auto_install` off or
install a TFT once with `nspanel_haui.update_tft` and `url` (it then stays until
the firmware changes). To leave the test, clear the **Firmware manifest URL**:
the hub then offers the latest GitHub release when it is newer than the test
build, or install a release with `nspanel_haui.update_firmware` and `version`.

## Branches and cadence

`master` is **release-only**. Normal work never lands there directly: it arrives
through a `release/X.Y.Z` branch cut from `dev`. A release hotfix may branch
from `master` when a patch cannot wait for the next `dev` cycle. Every tag is
cut from a commit whose CI was green on its source branch.

- `master` — release branch. Receives release branches cut from `dev`; release
  hotfixes branch from `master` only when a patch cannot wait. Every tag `vX.Y.Z` is cut from a
  green commit here. GitHub Pages deploys from this branch and Marketplace users
  install from its releases. Protected by the "Protect master (release-only)"
  ruleset: no direct pushes, no force-pushes, no deletion, and a merge needs a
  PR with the always-running CI checks green.
- `dev` — integration branch, the target for all day-to-day work, and the
  repository's **default branch**, so new PRs base on it automatically. CI runs
  here on every push and PR; each push also builds a versioned universal dev
  firmware prerelease with commit-linked notes (see
  [Published development firmware](#published-development-firmware)).
- Feature branches — branch off `dev`, open the PR against `dev`.
- Release branches — `release/X.Y.Z`, cut from `dev` for release prep and merged
  into `master` through a PR.
- Hotfix branches — branch off `master` only when a released version needs a
  patch that cannot wait for the next `dev` cycle; PR into `master`, tag, then
  merge `master` back into `dev`.

The cycle in one line: feature → PR into `dev` → cut `release/X.Y.Z` from `dev`
→ release prep there (version bump, CHANGELOG, release notes, TFTs) → PR
`release/X.Y.Z` → `master` → tag on `master` → `release.yml` publishes → merge
`master` back into `dev` → open the next CHANGELOG section.

**Why release prep never happens on `dev`:** every push to `dev` makes the
development-firmware workflow commit the next dev version back onto the branch
([Published development firmware](#published-development-firmware)). That
breaks a release PR straight from `dev` twice over:

- The stable version bump is overwritten within minutes: `dev` reads `X.Y.Z`
  and the bot commits `X.Y.(Z+1).devN` on top, so the tag check in
  `release.yml` fails.
- The tip of `dev` is always the bot's `[skip ci]` commit, pushed with the
  workflow token. GitHub runs no `push` or `pull_request` workflows for a PR
  whose head commit says `[skip ci]`, so the PR's required checks never report
  and the `master` ruleset (no bypass actors) blocks the merge.

A `release/X.Y.Z` branch avoids both: no workflow commits to it, and its head is
your own commit, so the PR's checks run. It starts with the dev version on it;
`scripts/bump_version.py X.Y.Z` sets the stable version there.

Commits use [Conventional Commits](https://www.conventionalcommits.org/)
(`feat`, `fix`, `docs`, … with an optional scope), so the merged history reads
like a changelog. Keeping that log is manual: each release prep collects the
merged commits into the `CHANGELOG.md` section (heading plus date, one line per
change), describes them in detail in `.github/release-notes/<tag>.md` for the
release body, and writes the `docs/upgrading.md` entry for breaking changes —
none of the release tooling generates any of them (see
[step 5](#5-release-notes-and-tagging) for what goes where).

Enforcement: the `master` ruleset blocks direct pushes, force-pushes and branch
deletion, and requires a pull request whose always-running checks are green
before merge. It has **no bypass actors**, so the release merge goes through a
PR like everything else. Tags are unaffected: the ruleset does not
gate them, and `release.yml` fires on any `v*` tag pushed anywhere (see
[Versioning and tag policy](#versioning-and-tag-policy)) — that tags are cut on
green `master` commits is policy, not workflow enforcement. To add an escape
hatch, add a bypass actor to the ruleset rather than weakening the rules.

`dev` itself is not protected: it takes direct pushes and PRs alike. Add a
ruleset there if the branch starts collecting unreviewed changes.

No fixed calendar. Ship when user-visible changes accumulate or a fix cannot
wait. The **0.4.x line is a hard gate**: it finishes the binary and TFT install
and proves the base and core functions before any v0.5 work starts. Patch
releases in that line close regressions and gate failures; minor releases
(`0.5.0`) ship features and breaking changes. **Any breaking change must ship
with a `docs/upgrading.md` entry and a CHANGELOG "Breaking changes" section** —
no alias is kept as a fallback, so the upgrade guide is the only migration path.

## CI gates and local checks

| Workflow | Triggers | What it enforces |
|----------|----------|------------------|
| `tests.yml` | pushes/PRs to `master`, `dev` | `zensical build --strict`; icon cheatsheet, translation and version-source freshness; Nextion asset gate (`verify_nextion.py --require-portrait`); `pytest tests/`; `ruff check custom_components/ scripts/`; `mypy`; `node --test 'tests/frontend/*.test.mjs'`; `esphome config esphome/nspanel_haui_universal.yaml` |
| `docs.yml` | docs, docs-tooling or config changes on pushes/PRs to `master`, `dev`; manual dispatch | `zensical build --strict`; deploys Pages from `master` only |
| `validate.yml` | pushes/PRs to `master`, `dev`; nightly; manual dispatch | hassfest and HACS validation |
| `screens.yml` | each completed `Development Firmware` run on `dev`; manual dispatch | regenerates the screen overview (`gen_preview_gallery.py --docs`: `docs/screens.html`, `docs/assets/screens/`) and commits it to `dev` with `[skip ci]` when it changed |
| `release.yml` | `v*` tags; manual dispatch | tag vs `manifest.json` version; Nextion release gate (`verify_nextion.py --require-portrait` and `gen_portrait.py --check`); ESPHome config + compile; firmware manifest (tag refs only); prepared release notes; asset upload |

**Release-only checks:** the tag-vs-`manifest.json` version check,
`gen_portrait.py --check` (the spec-vs-HMI attribute gate), the ESPHome
*compile* (push/PR CI only runs `esphome config`), the firmware-manifest
generation, and the GitHub release with its asset upload run only in
`release.yml` on a tag push. Push/PR CI validates the Nextion assets, version
consistency and the firmware config, but never compiles or publishes.

**Gap to keep in mind:** a tag push does **not** re-run `tests.yml` — only
`release.yml` runs, and it adds the release-only checks above on the tag
itself. The tag build trusts that the tagged commit was already green
on a branch. Cut tags only from a passing `master` commit, and re-check
`git status` for uncommitted work first.

### Run the same gates locally

Every command below is what CI runs. Run them before opening a PR or cutting a
tag; release prep is not finished until they pass on the final commit.

```bash
# Documentation and generated assets
zensical build --strict
python3 scripts/gen_fonts/gen_cheatsheet.py && git diff --exit-code -- docs/cheatsheet.html
python3 scripts/translations/extract_translations.py && git diff --exit-code -- custom_components/nspanel_haui/haui/locale scripts/translations/translate.json

# Version and Nextion gates
VERSION=$(python3 -c "import json; print(json.load(open('custom_components/nspanel_haui/manifest.json'))['version'])")
python3 scripts/bump_version.py "$VERSION" --check  # add --tft-update for a TFT release
python3 scripts/verify_nextion/verify_nextion.py --require-portrait
python3 scripts/gen_portrait/gen_portrait.py --check

# Backend, lint and type checks
pytest tests/
ruff check custom_components/ scripts/
mypy

# Frontend tests
node --test 'tests/frontend/*.test.mjs'

# Firmware config (install requirements-esphome.txt first)
esphome config esphome/nspanel_haui_universal.yaml
```

`python3` may be `python` in your environment; on this repo's dev venv use
`.venv/bin/python` (or activate `.venv` first). The ESPHome check needs the
pinned toolchain from `requirements-esphome.txt`.

## Release runbook

### 1. Pre-flight (a few days before)

- Confirm `dev` and `master` are green (tests, frontend, docs, hassfest/HACS).
- Confirm the device passlist in the
  [Roadmap's v0.4.x section](https://github.com/happydasch/nspanel_haui/blob/master/ROADMAP.md#v04x--finishing-the-binary-and-tft-install-current-focus)
  passed on real EU and US hardware. The 0.4.x line is a hard gate: v0.5 work
  does not start until every row is green.
- Freeze features; only fixes land from here.
- Decide the version number and check for pending breaking changes.

Before release work, install the repository's [optional pre-commit
checks](development.md#git-hooks) so virtual-layout assets are regenerated and
portrait layout drift is caught before CI.

### 2. Version bump

Cut the release branch from an up-to-date `dev` (it carries the bot's dev
version, which the bump replaces):

```bash
git switch dev && git pull
git switch -c release/0.5.0
```

Run the bump script on that branch. The firmware version advances on every release, but the
TFT version changes only when the release includes a display update:

```bash
python3 scripts/bump_version.py 0.5.0                         # firmware-only release
python3 scripts/bump_version.py 0.5.0 --tft-update            # release with a new TFT
python3 scripts/bump_version.py 0.5.0 --check --tft-update     # dry run
```

Every run updates `manifest.json`, `pyproject.toml` and ESPHome `yaml_version`.
Only `--tft-update` also updates ESPHome `tft_version` and both HMI
`system.tftVersion` values. Firmware reports the latter separately as
`tft_required_version`, so a firmware-only release can use the previous TFT
without creating a display update offer. The release manifest takes its TFT
version from `esphome/nspanel_haui/version.yaml`.

The script edits HMI files in place; that is only legal for a same-length TFT
version change (`0.4.2` → `0.4.3`). A shorter or longer value resizes the
attribute record and the script refuses it — use the Nextion Editor for that
bump. The script does not touch `CHANGELOG.md`, so add or update its section and
date by hand. Recompile both TFTs after a `--tft-update`; the release gate
rejects stale HMI/TFT assets.

`scripts/bump_tft_version.py` bumps only the HMI `tftVersion` text; the combined
script above calls it for `--tft-update`. Both are importable and covered by
`tests/test_bump_version.py`.

### 3. Nextion assets (human, GUI-only)

1. Open `nextion/nspanel_haui.HMI` in Nextion Editor and make or verify the
   release's display changes. With `--tft-update`, the version bump already wrote
   `system.tftVersion` into both HMIs for a same-length bump — only a
   length-changing version (which the script refuses) needs the manual
   `system.tftVersion` edit here.
2. Compile `File → TFT file output` → `nextion/nspanel_haui.tft`.
3. Re-run `python3 scripts/gen_portrait/gen_portrait.py` so the portrait HMI
   picks up landscape edits, then compile
   `nextion/nspanel_haui_portrait.tft`. The recompile is mandatory after any
   `PORTRAIT_ATTRS`/HMI change — the committed HMI alone does not reach
   devices. `gen_portrait.py --check` verifies attribute values as well as
   widget coverage, so an attribute-only change fails the gate until the HMI
   is regenerated.
4. The Nextion gates are part of [Run the same gates locally](#run-the-same-gates-locally).
   Also run `python3 scripts/check_preview_coverage.py` to confirm every
   exposed panel still resolves to a physical page in both preview layouts.

### 4. Docs and firmware

- Update user-facing docs for behaviour changes (install, services, display
  models).
- Breaking changes: write the `docs/upgrading.md` entry, the CHANGELOG
  "Breaking changes" line and the release notes' "Before updating" entry during
  release prep on the release branch.
- Verify the universal firmware still validates:
  `esphome config esphome/nspanel_haui_universal.yaml`.
- The universal binary serves **any number of panels**: the MAC suffix gives
  each device a unique name and access point, so no per-device build is needed.
  The baked API/OTA/web credentials remain shared — keep that caveat documented.

### 5. Release notes and tagging

Prepare the GitHub release body in `.github/release-notes/<tag>.md` (for example
`.github/release-notes/v0.4.5.md`) during release prep on the release branch,
before the merge to `master`. Because `master` takes no direct commits, the merge carries the file
to the tagged commit. `release.yml` publishes it as the release body and falls
back to the changelog pointer when no file exists.

The changelog and the release notes split the work:

- **`CHANGELOG.md` is the compact index** — one line per change (two at most),
  grouped as *Breaking changes*, *Added*, *Changed* and *Fixed*: what changed,
  in the user's terms, with its issue or PR link. A breaking change links its
  `docs/upgrading.md` section. No background, no cause, no implementation
  detail.
- **The release notes carry the detail** — for every changelog line, what the
  change does, why it was needed and what a user notices; what to do before
  updating; known limits; the contributors and a compare link. Group long
  lists under headings (for example *Before updating*, *New*, *Changed* and
  *Fixed* by area). Repository-relative links (`docs/upgrading.md#…`) work:
  GitHub resolves them against the tag.

Credit external contributors by their GitHub handle in both, and keep
individual maintainer names out of the release body.

After the merge lands on `master`, tag and publish:

```bash
git tag -a vX.Y.Z -m "NSPanel HAUI X.Y.Z"
git push origin vX.Y.Z
```

The tag push starts `release.yml`, which checks that the tag matches
`manifest.json`, runs the Nextion gate, validates and compiles the universal
firmware, and attaches the two firmware images, both TFTs and
`firmware-manifest.json` to the GitHub release. Watch the run; do not announce
before it is green.

### 6. Post-release

- Verify the release page carries the two firmware images (`nspanel_haui.bin`,
  `nspanel_haui_ota.bin`), both TFTs and `firmware-manifest.json` with the
  expected names, and that the body shows the prepared release notes.
- Flash one panel from the published `.bin` and confirm TFT auto-update, as a
  smoke test of the exact published artifacts.
- Announce; link the release notes.
- Merge `master` back into `dev`, then open the next `CHANGELOG.md` section.
  Because `dev` carries the latest dev version (e.g. `0.5.0.dev12`) while
  `master` carries the released stable `X.Y.Z`, the merge-back now conflicts in
  `custom_components/nspanel_haui/manifest.json` and
  `esphome/nspanel_haui/version.yaml`; resolve both to the stable version so the
  next dev build derives `X.Y.(Z+1)` again.

### 7. Rollback

If the published assets are broken: mark the GitHub release as a draft (or
delete it) and publish a patch release. The update controller only installs the TFT required by the firmware's
`tft_required_version`, so a corrected tag with matching firmware and TFT
versions is enough; never re-point an existing tag at different bytes.

## Guardrails and known gaps

These are the places the process can still go wrong; check them during release
prep.

**Version and release notes**

- **Firmware and TFT version sources** — `manifest.json`, `pyproject.toml`,
  ESPHome `yaml_version`, `tft_version` and both HMI files. Firmware-only
  releases leave the TFT version fields unchanged; `--tft-update` updates them
  together, and CI catches drift in the selected mode.
- **Tag pushes skip `tests.yml`** — only `release.yml` runs on a tag. Tag only a
  commit that was green on its source branch.
- **Release notes are a separate file from the changelog** —
  `.github/release-notes/<tag>.md` becomes the release body when present;
  otherwise `release.yml` publishes only a pointer to the changelog, whose
  one-line entries carry no detail. Prepare the file for every tag and keep the
  two in sync: every changelog line has its detail in the notes.

**Nextion (GUI-only)**

- **The Nextion Editor is GUI-only** — TFT compilation cannot be scripted. The
  version bump is scripted only for same-length versions, and the release gate
  can only verify the result.
- **The portrait TFT derives from the landscape HMI** — regenerate it after every
  landscape edit. Forgetting the step fails the gate or ships a stale portrait.
- **Asset names are frozen** — renaming one silently breaks auto-update for
  flashed panels. Add variants without renaming existing assets.

**Distribution**

- **~120 MB of Nextion binaries live in git** — Marketplace downloads include them; repo
  and zip size grow with every TFT rebuild. Git LFS or release-only storage is
  planned.
- **The universal binary bakes shared credentials** — MAC suffixes give each
  device a unique name and access point, but the API/OTA/web credentials are
  shared. Credential isolation is not solved.
- **ESPHome is pinned to a minimum version** — `base.yaml` defines the floor and
  `requirements-esphome.txt` pins the build toolchain. Bump both together.

Planned improvements to this setup are tracked in the
[Roadmap](https://github.com/happydasch/nspanel_haui/blob/master/ROADMAP.md#release-tooling).
